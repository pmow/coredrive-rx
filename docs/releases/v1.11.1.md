# CoreDrive RX v1.11.1

A field log showed 59 receptions buffered and **not one published**, alongside ~18
`Keepalive timeout` errors against a single successful connect. Probing the broker from
a fixed line ruled out the obvious suspects — publishes to `/packets`, `/rf` and
`/regions` were all acknowledged in ~85 ms with `returnCode=0` and no disconnect, and a
deliberate same-clientId takeover makes the victim report a bare `close`, never a
keepalive error. Neither the ACL nor session contention was involved. Two defects were.

## What's new

- **The queue can now make progress on a link that keeps dropping.** `drain()` collected
  published ids and removed them from the queue only *after* the whole loop finished, so
  one rejecting publish threw and every record the broker had **already acknowledged**
  stayed queued to be sent again. Publishes are sequential, so a 59-record backlog needs
  about 5 s of continuous connectivity at 86 ms round-trip and ~18 s at 300 ms. On a
  mobile link that stayed up for roughly a second at a time, that design could never
  commit anything at all. Progress is now committed as it is earned: a record is removed
  if and only if the broker acknowledged it.

- **One bad record can no longer block the whole queue.** A reception that repeatedly
  fails to publish is stepped over rather than retried forever at the head of the queue,
  where it stopped everything behind it. It is kept, not discarded. A *link* drop is
  charged to the link and not to the record, so a run of drops cannot quarantine a
  perfectly good reception.

- **A retired MQTT client can no longer masquerade as the live one.** Every `Publisher`
  ever created reported into a single handler writing a single global broker state, so an
  orphaned client's endless 4-second reconnect loop overwrote a healthy connection's
  status and filled the debug log with failures nothing could attribute. Each publisher
  now carries an id; events from a retired one are named once and then ignored.

- **Connecting no longer claims an uplink it does not have.** It used to adopt an
  existing publisher without checking it, printing `③ CoreScope connected ✓` over a
  client that was in fact looping. A publisher that is not connected is retired — which
  also stops its reconnect loop — and a fresh one is built.

- **`Keepalive timeout` is now evidence instead of a red herring.** The keepalive value is
  set explicitly and quoted in the log next to the CONNACK return code. mqtt.js arms its
  keepalive manager only inside `_onConnect`, and only when one does not already exist,
  never re-arming an existing manager — so a manager that survives a connection can
  report a timeout on a perfectly healthy link.

## Upgrade notes

- **Service-worker cache bumped `coredrive-rx-v37`.** Clients pick up the new bundle on
  their next load with a connection.
- **No config or data migration.** The MQTT payload contract with the CoreScope ingestor
  is unchanged. Anything already queued on a device is published by the new code.
- **Duplicate rows may exist server-side from before this release.** Every drain that was
  interrupted mid-flush re-sent the records it had already delivered. If your ingestor
  does not de-duplicate on `(origin_id, timestamp, raw)`, expect repeats in
  `client_receptions` for the affected period.
- **The EMQX ACL must allow all three subtopics** (`/packets`, `/rf`, `/regions`). The
  setup instructions listed only `/packets` until v1.11.1 — see the README note on what a
  denied publish actually does, since with EMQX's default `deny_action=ignore` it is
  silently dropped and still acknowledged.
- Tests: 234 pass (+14). The queue-draining rules are covered in `test/drain.test.mjs`
  against a publisher whose link dies mid-flush.
