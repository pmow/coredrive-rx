# CoreDrive RX v1.11.0

Diagnosability release. Two field logs turned out to share one root cause that the app
was structurally unable to report, so this release is mostly about making the app say
what is wrong — and about never losing coverage data to a configuration problem.

## What's new

- **A failed `config.json` fetch no longer disables a whole session in silence.** The
  config was fetched exactly once at startup and never retried. One transient failure —
  a cold start in a garage, cellular not up yet — left the app with no config for the
  rest of the session: no MQTT publisher was ever built, and every feature flag read as
  off. It captured for an hour, published nothing, and reported **"✅ All connected —
  capturing"** the whole time. The config is now retried on every connect, on the
  `online` event, and once a minute while it is missing, and uploading comes up on its
  own the moment it arrives — no reconnect, no restart.

- **A degraded uplink is now visible on the Home screen.** A red banner stays up
  whenever receptions are being buffered but not uploaded, and it says explicitly that
  nothing is being thrown away — a driver who thinks the data is lost stops driving. The
  connection progress list no longer claims an uplink it does not have.

- **"Push pending now" tells the truth and actually recovers.** It used to answer
  `nothing pending / not connected` for a healthy empty queue, a dead link, and hundreds
  of buffered records alike — because `drain()` returns 0 for all three. Worse, its
  reconnect path was guarded in a way that skipped the one case that most needed it (no
  publisher at all). It now reports queue depth independently of link health and picks
  the repair that matches the actual fault.

- **Every exported debug log carries a diagnostic header.** Share log now stamps the app
  version, the **effective** config flags, the companion firmware version, whether region
  discovery can transmit at all, the uplink state and the queue depth. Built at share
  time, so it can never roll out of the 200-line ring buffer the way a startup line does.
  Both field logs arrived with no way to tell which version wrote them.

  ```
  === CoreDrive RX debug log ===
  app        v1.11.0
  config     loaded — fullRfLog=on rfSampler=off regionDiscovery=off
  firmware   v13
  regions    inert — regionDiscovery is off in config.json
  uplink     ok — 0 pending
  log lines  200 (buffer full — older lines have rolled out)
  ==============================
  ```

- **Region discovery says why it is inert.** Its four gates all returned early in
  silence, so "no `regions` lines in the log" was consistent with every one of them and
  distinguished none. It now names the blocking gate once, in the log, so it survives
  into a shared export.

- **Feature flags default to on.** An absent `fullRfLog` / `rfSampler` /
  `regionDiscovery` key in an existing `config.json` now means **on**. A config written
  before those keys existed reported the features off while the served file said on,
  which is indistinguishable from the features being broken. An explicit `false` still
  wins. With **no** config loaded at all the two logging features still apply, so the
  session keeps collecting and the queue publishes once config arrives; `regionDiscovery`
  does not, because it is the only feature that transmits and repeaters rate-limit
  anonymous requests to 4 per 180 s shared across every requester.

- **`config.json` is never served from the offline cache.** A copy cached in an earlier
  era silently disabled every flag added since. A stale config is worse than none: none
  is a state the app detects, warns about and retries; stale looks perfectly healthy.
  The service worker's app-shell fallback is also limited to navigations now — handing
  `index.html` to a JSON request is what turned an offline start into the baffling
  `invalid JSON — Unexpected token '<'`.

## Upgrade notes

- **Service-worker cache bumped `coredrive-rx-v35` → `v36`.** Clients pick up the new
  bundle on their next load with a connection.
- **Behaviour change — absent flags now mean ON.** If your CoreScope ingestor does not
  have `clientRxObservations.enabled` / `clientRfSamples.enabled` / `clientRegions.enabled`,
  or your broker ACL does not permit the `/rf` and `/regions` subtopics, set those flags
  explicitly to `false`. Per the standing warnings in the README, `fullRfLog` multiplies
  upload volume and an ACL-denied publish is still PUBACKed under MQTT 3.1.1 — the app
  logs `published N record(s)` and looks healthy while the server stores nothing.
  `config.example.json` has been updated to the new defaults.
- **Starting the app now needs a live connection once**, because `config.json` is no
  longer cached offline. Capture and buffering are unaffected by a cold start with no
  network — only uploading waits, and the queue drains as soon as the config loads.
- **No data or config migration.** The MQTT payload contract with the CoreScope ingestor
  is unchanged.
- Tests: 220 pass (+41). `sw.js` is now driven in a `node:vm` ServiceWorkerGlobalScope,
  so the file that actually ships is tested rather than a copy of its logic.
