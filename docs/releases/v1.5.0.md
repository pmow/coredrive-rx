# CoreDrive RX v1.5.0

## What's new

- **Optional full RF logging.** Until now the app threw away every reception it could not
  attribute to a directly-heard node — DIRECT-route packets, 1-byte path hashes, anything
  without a usable last forwarder. Those packets were received, with signal strength and a
  GPS fix, and discarded before they were ever queued. With **`fullRfLog`** enabled they are
  uploaded too, so CoreScope can record the routing scope, the full forwarder chain, the
  path-hash size and the route type of everything you hear. **Zero extra airtime** — nothing
  new is transmitted; this is only about keeping what the radio already handed us.

- **RF environment sampler.** Everything the app recorded was anchored to a *packet*. But a
  drive also passes through RF conditions that exist whether or not a packet arrives: the
  noise floor, how busy the channel is, how many receptions fail CRC. The radio measures all
  three and was never asked. With **`rfSampler`** enabled the app samples those counters
  along the GPS track — every **15 s while moving**, every **5 min while parked** — so the
  server can build a noise-floor map, a channel-utilisation map and a CRC-error-rate map.
  A fixed observer cannot produce those: it measures one point forever. Again **zero
  airtime**: these are local Bluetooth queries to the attached radio.

## Upgrade notes

- Service-worker cache bumped to `coredrive-rx-v18` — **hard-refresh / restart the PWA** to
  pick up the new assets.
- **Both features are off by default.** Nothing changes until you set them in `config.json`.
- **`fullRfLog` requires `clientRxObservations.enabled` on the CoreScope ingestor.** With the
  server gate off, the phone spends mobile data uploading packets the server decodes and
  discards — no row written, no warning anywhere. Enable the server side first.
- **`rfSampler` requires the broker ACL to permit the `/rf` subtopic**, plus
  `clientRfSamples.enabled` on the ingestor. MQTT 3.1.1 PUBACK carries no reason code, so a
  denied publish is still acknowledged and logged as success — it would look like it is
  working while the server receives nothing.
- Expect **2–3× the normal upload volume** with `fullRfLog` on.
- No data migration on the app side.
