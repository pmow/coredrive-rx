# CoreDrive RX v1.11.2

A clean v1.11.1 field log confirmed the previous release's fixes — the 59-record
backlog went out in one pass four seconds after connecting, with a single publisher,
`connack rc=0`, no retired-publisher events and no keepalive timeouts. The 4-second
reconnect loop is gone.

It also exposed one more way the same queue could duplicate data.

## What's new

- **Two drains can no longer publish the same records.** `drain()` had no mutual
  exclusion and four uncoordinated callers: the 5 s drain loop, the broker `connect`
  event, the `online` event and the **Push pending now** button. Two overlapping passes
  each take their own snapshot of the queue, so both see — and both deliver — the rows
  the other has not committed yet. In the log this read as `published 59 record(s)`
  followed one second later by `published 49 record(s)` for a queue that had held 59:
  the second pass began just after the first committed its opening batch of ten, found
  the other 49 still queued, and sent every one of them to the ingestor again. Only one
  pass now runs at a time; a caller arriving mid-pass joins it and gets its result.

  This hole predates v1.11.1 — the old all-or-nothing drain could double-publish just as
  easily — but committing progress in batches is what made it visible in a log.

## Upgrade notes

- **Service-worker cache bumped `coredrive-rx-v38`.** Clients pick up the new bundle on
  their next load with a connection.
- **No config or data migration.** The MQTT payload contract is unchanged.
- **Duplicate rows from before this release remain.** Both the interrupted-drain bug
  (fixed in v1.11.1) and this concurrency bug re-sent records the broker had already
  accepted. If your ingestor does not de-duplicate on `(origin_id, timestamp, raw)`,
  expect repeats in `client_receptions` for the affected period.
- Tests: 237 pass (+3).
