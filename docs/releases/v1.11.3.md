# CoreDrive RX v1.11.3

A session left open while the phone slept came back wedged: the broker reconnected
every four seconds for three minutes and published nothing, until the app was
restarted. The v1.11.2 diagnostics are what made that log readable, and they point at
the timer mqtt.js schedules its keepalive on, not at the link.

## What's new

- **A slept-through session no longer wedges the uplink in a keepalive loop.** In the
  field log the CONNACK at `17:02:26` and `CoreScope error: Keepalive timeout` carry the
  same timestamp, and every reconnect after it repeated that pair at the 4 s
  `reconnectPeriod`, with 20 records left pending.

  mqtt.js defaults to `timerVariant: 'auto'`, which in a browser runs the keepalive
  interval through worker-timers: the page hands `performance.timeOrigin +
  performance.now()` to a Worker, which compares it against its own clock. That Worker is
  created lazily, on the first connect, so it takes its time origin from the wall clock at
  that moment, while the page's `performance.now()` does not advance while an Android
  device sleeps. This app had been open since `09:45:34` and was picked up again at
  `17:02:25`, so the Worker was handed a "now" hours in the past: every keepalive tick was
  already overdue, it fired three back to back, and the counter passed its threshold
  within milliseconds of the CONNACK. mqtt.js arms a fresh keepalive manager on every
  CONNACK, so each reconnect met the same skew, and the Worker is a module singleton, so
  retiring the publisher and building a new client could not have cleared it either. Only
  a page reload, which resets `performance.timeOrigin`, ended it, which is exactly what
  the field report said.

  The keepalive interval is now pinned to `timerVariant: 'native'`, which is measured in
  one clock domain and cannot drift that way. The connect options moved into
  `Publisher.connectOptions()` so they can be asserted without opening a socket.

## Upgrade notes

- **Service-worker cache bumped to `coredrive-rx-v39`.** Clients pick up the new bundle
  on their next load with a connection.
- **No config or data migration.** The MQTT payload contract is unchanged.
- **A native timer is throttled while the page is in the background.** Worst case that
  costs one keepalive timeout, which the ordinary reconnect recovers from, in place of a
  loop that only a restart ended. During a normal capture run the screen wake lock keeps
  the page in the foreground anyway.
- **Not reproduced on a device.** The mechanism is read off the field log plus the
  mqtt.js 5.15.1 and worker-timers sources. Confirming it needs a session left to sleep
  for hours and then picked up again.
- Tests: 239 pass (+2).
